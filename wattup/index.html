ON-PREMISE vs EKS

EKS 같은 관리형 서비스는 내부 동작을 추상화합니다. 스케줄링, 네트워킹, 스토리지를 직접 다뤄야 나중에 EKS도 제대로 쓸 수 있다고 판단했습니다. 또한 회사 환경에서는 비용 문제로 직접 구축하는 경우가 많습니다.

KUBEADM vs minikube

minikube는 단일 노드 실습용입니다. kubeadm으로 멀티 노드(master + worker 3개) 클러스터를 직접 구성하여 노드 간 네트워킹, pod 스케줄링, CNI 동작을 실제 환경에 가깝게 경험했습니다.

Troubleshooting

트러블슈팅

01Tailscale 설치 이후 Kubernetes 네트워크 연쇄 장애 발생▼
흐름

Tailscale 설치 이후 Pod Network·Service Routing 장애가 발생하고, CoreDNS·local-path-provisioner CrashLoop → PVC 생성 실패 → Kafka Pending으로 장애가 연쇄 전파되었습니다.

증상

CoreDNS·Calico controller·local-path-provisioner CrashLoop과 Kafka PVC Pending이 동시에 발생했습니다.

영향

DNS와 Service Routing, 스토리지 프로비저닝이 함께 중단되며 데이터 워크로드까지 연쇄적으로 영향을 받았습니다.

판단

개별 애플리케이션 장애가 아니라 여러 증상이 공유하는 하위 네트워크 레이어 문제로 판단했습니다.

02Service Routing 검증을 통한 CNI 레이어 원인 특정▼
확인

API Server 직접 통신, worker별 Service IP 접근, ip route, kube-proxy 로그, Pod 내부 통신을 순서대로 확인했습니다.

검증

kube-proxy 재시작과 임시 route 추가로 일부 통신이 복구됐지만, Pod 내부 Service IP 통신 장애가 반복돼 근본 해결이 아님을 확인했습니다.

축소

노드·Pod·Service 구간을 단계별로 비교해 장애 범위를 CNI 레이어와 Calico의 Node IP 자동 감지로 좁혔습니다.

원인

Calico가 실제 내부망 인터페이스 대신 Tailscale VPN 인터페이스를 선택하면서 클러스터 라우팅이 무너졌습니다.

03Calico 재설치 및 인터페이스 고정으로 전체 워크로드 복구▼
보호

CNI 재설치 전 PostgreSQL·MongoDB·Kafka StatefulSet을 scale down해 인프라 변경 중 데이터 워크로드 영향을 최소화했습니다.

조치

Calico 제거 → tunl0 및 CNI 설정 잔재 정리 → Calico 재설치 → IP autodetection을 실제 노드 인터페이스로 고정했습니다.

결과

Kafka·MongoDB·PostgreSQL·Importer·Kafka UI·Backend 전체 워크로드를 Running으로 복구했습니다.

재발 방지

Tailscale 설치 전 인터페이스 고정, --accept-routes=false 적용, 노드 라우팅 검증을 체크리스트로 남겼습니다.

04Tailscale → K8s DNAT 구성 후 TCP 응답 경로 장애▼
현상

DNAT 설정 후에도 SYN 패킷만 반복. SYN-ACK 없음 (tcpdump로 확인).

원인

DNAT으로 요청은 worker3의 NodePort까지 전달됐지만, 반환 경로에 SNAT이 없어 요청·응답 경로가 비대칭으로 형성됐습니다.

해결

Master의 POSTROUTING에 MASQUERADE를 적용해 응답 트래픽이 Master를 거쳐 Tailscale로 반환되도록 구성했고, TcpTestSucceeded: True로 정상 연결을 확인했습니다.

학습

포트 전달은 요청 경로만 열어서는 완성되지 않으며 응답 경로의 대칭성까지 확인해야 합니다. 이후 DNAT과 MASQUERADE를 하나의 설정 단위로 관리하도록 체크리스트화했습니다.

05Vite 빌드 타임 환경변수로 인한 배포 환경 불일치▼
현상

다른 환경에 프론트엔드 컨테이너를 배포해도 API 요청이 기존 학원 PC 주소로 전송되어 서비스에 연결되지 않았습니다.

원인

Vite는 빌드 타임에 환경변수를 JS 번들에 직접 삽입하므로 런타임 변경이 불가능하며, .env.production의 기존 API 주소가 빌드된 JS 번들에 포함되어 있었습니다.

해결

배포 대상의 API 주소를 빌드 인자로 전달하고 캐시 없이 이미지를 다시 생성해, 새 주소가 포함된 프론트엔드 번들을 배포했습니다.

학습

Vite 환경변수는 컨테이너 실행 시점이 아니라 빌드 시점에 결정된다는 점을 확인했습니다. 이후 환경별 빌드 절차를 분리했으며, 장기적으로는 Nginx를 이용한 런타임 설정 주입 구조를 고려했습니다.

06OCI 호스트 nftables FORWARD 정책으로 컨테이너 외부 접근 차단▼
현상

OCI 인스턴스 내부 localhost에서는 서비스가 정상이지만 외부에서는 접근할 수 없었습니다.

원인

클라우드 네트워크 설정과 컨테이너 자체는 정상이었지만, 호스트 nftables FORWARD 체인의 reject with icmp type host-prohibited 규칙이 컨테이너 전달 트래픽을 차단하고 있었습니다.

해결

nftables 정책에서 컨테이너 포워딩을 차단하던 규칙을 조정하고 영구 저장해 외부 요청이 Podman 컨테이너까지 전달되도록 복구했습니다.

학습

클라우드 Security List뿐 아니라 호스트 방화벽과 컨테이너 런타임의 패킷 전달 정책까지 함께 확인해야 함을 배웠습니다.

Retrospective

배운 점

장애 분석 원칙

DNS·PVC·Kafka 장애를 각각 처리하기보다 공통 기반인 CNI와 Service Routing을 먼저 확인하며 원인을 좁혔습니다. kube-proxy 재시작과 수동 route는 증상을 일시적으로 완화했지만 재발했고, 이를 통해 임시 복구와 근본 복구를 구분해야 한다는 점을 배웠습니다.

재발 방지 절차

CNI 재설치 전 StatefulSet을 scale down해 데이터를 보호하고, CNI 상태 초기화와 인터페이스 감지 기준 고정으로 근본 복구했습니다. 이후 Tailscale 설치 전 IP autodetection 설정 → --accept-routes=false → 노드 라우팅 검증을 체크리스트화했습니다. 문제 해결 절차는 증상 확인 → 장애 레이어 축소 → 임시 조치 검증 → 근본 원인 복구 → 재발 방지 순서로 정리했습니다.
