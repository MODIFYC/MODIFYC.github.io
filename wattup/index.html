ON-PREMISE vs EKS

EKS 같은 관리형 서비스는 내부 동작을 추상화합니다. 스케줄링, 네트워킹, 스토리지를 직접 다뤄야 나중에 EKS도 제대로 쓸 수 있다고 판단했습니다. 또한 회사 환경에서는 비용 문제로 직접 구축하는 경우가 많습니다.

KUBEADM vs minikube

minikube는 단일 노드 실습용입니다. kubeadm으로 멀티 노드(master + worker 3개) 클러스터를 직접 구성하여 노드 간 네트워킹, pod 스케줄링, CNI 동작을 실제 환경에 가깝게 경험했습니다.

Troubleshooting

트러블슈팅

01PostgreSQL CrashLoopBackOff securityContext 권한 오류▼
현상

PostgreSQL Pod가 볼륨에 접근하지 못하고 CrashLoopBackOff 상태를 반복했습니다.

원인

local-path-provisioner가 PVC 디렉토리를 root 소유로 생성. runAsUser: 999를 함께 설정하면 오히려 권한이 없어짐.

해결

사용자와 그룹을 강제로 지정하던 설정을 제거하고, 볼륨 파일에 PostgreSQL 그룹 권한이 적용되도록 fsGroup만 지정해 정상적으로 데이터 디렉토리에 접근하도록 수정했습니다.

학습

컨테이너 실행 사용자뿐 아니라 볼륨을 생성하는 프로비저너의 소유권 방식까지 함께 확인해야 합니다. 이후 StatefulSet 배포 가이드에 fsGroup 적용 원칙을 명시했습니다.

02Kafka 데드락 KRaft 3-node 쿼럼 실패▼
현상

Kafka 첫 번째 Pod만 실행된 채 나머지 Pod가 준비되지 않아 클러스터 구성이 멈췄습니다.

원인

3-node KRaft는 과반수 노드가 동시에 떠야 리더 선출 가능. StatefulSet 기본 순차 실행으로 kafka-0 혼자 먼저 떠서 쿼럼 불가 → 데드락.

해결

Kafka Pod가 순차적으로 기다리지 않고 동시에 시작되도록 StatefulSet의 Pod 관리 정책을 병렬 방식으로 변경하고, 준비 상태 이전에도 노드끼리 주소를 찾을 수 있도록 Headless Service의 탐색 설정을 조정했습니다.

학습

분산 시스템의 배포 순서는 일반 애플리케이션과 달리 쿼럼 형성 조건을 먼저 고려해야 합니다. 이후 Kafka 배포 템플릿에 병렬 시작과 노드 탐색 설정을 기본값으로 반영했습니다.

03Calico + Tailscale 충돌 Pod 네트워크 전체 붕괴▼
현상

Tailscale 설치 후 Calico가 tailscale0을 노드 IP로 착각 → CoreDNS / kube-proxy / local-path-provisioner 연쇄 CrashLoop.

원인

Calico IP 자동 감지가 Tailscale VPN 인터페이스를 우선 선택. Pod 네트워크 라우팅 전체 붕괴.

해결

Calico가 실제 내부망 인터페이스만 노드 IP로 감지하도록 대상을 고정하고, Tailscale이 외부 라우트를 받아 CNI 경로를 변경하지 않도록 설정해 Pod 네트워크를 복구했습니다.

학습

한 노드에 CNI와 VPN 인터페이스가 함께 존재하면 자동 감지에 의존해서는 안 됩니다. 이후 VPN 설치 전에 Calico 인터페이스를 고정하고 설치 후 전체 노드의 CNI 상태를 확인하는 절차를 문서화했습니다.

04Tailscale → K8s DNAT + MASQUERADE TCP 연결 실패▼
현상

DNAT 설정 후에도 SYN 패킷만 반복. SYN-ACK 없음 (tcpdump로 확인).

원인

DNAT으로 요청은 worker3으로 전달되나 응답 패킷 출발지가 worker3 IP → 클라이언트가 예상 못한 IP로 판단 거부. MASQUERADE 누락.

해결

Tailscale로 들어온 요청을 worker3의 NodePort로 전달하도록 DNAT을 구성하고, 반환 패킷도 동일한 경로로 돌아가도록 출발지 주소 변환을 함께 적용했습니다. 설정은 재부팅 후에도 유지되도록 영구 저장했습니다.

학습

포트 전달은 요청 경로만 열어서는 완성되지 않으며 응답 경로의 대칭성까지 확인해야 합니다. 이후 DNAT과 MASQUERADE를 하나의 설정 단위로 관리하도록 체크리스트화했습니다.

05Vite 환경변수 하드코딩 런타임 주입 불가▼
현상

다른 환경에 프론트엔드 컨테이너를 배포해도 API 요청이 기존 학원 PC 주소로 전송되어 서비스에 연결되지 않았습니다.

원인

Vite는 빌드 타임에 환경변수를 JS 번들에 직접 삽입. 런타임 변경 불가. 기존 이미지에 학원 PC IP 하드코딩.

해결

배포 대상의 API 주소를 빌드 인자로 전달하고 캐시 없이 이미지를 다시 생성해, 새 주소가 포함된 프론트엔드 번들을 배포했습니다.

학습

Vite 환경변수는 컨테이너 실행 시점이 아니라 빌드 시점에 결정된다는 점을 확인했습니다. 이후 환경별 빌드 절차를 분리했으며, 장기적으로는 Nginx를 이용한 런타임 설정 주입 구조를 고려했습니다.

06운영체제별 컨테이너 배포 차이 Podman + nftables FORWARD 차단▼
현상

OCI 인스턴스에서 Podman 배포 후 외부 접근 불가. localhost는 정상.

원인

OCI는 Red Hat 계열 OS로 Podman 기본. nftables FORWARD 체인에 reject with icmp type host-prohibited규칙이 컨테이너 포워딩 차단.

해결

호스트의 nftables 규칙을 점검해 컨테이너 포워딩을 차단하던 규칙을 제거하고, 변경된 방화벽 정책을 영구 저장해 외부 요청이 Podman 컨테이너까지 전달되도록 수정했습니다.

학습

클라우드 보안 목록이 열려 있어도 호스트 OS의 방화벽과 컨테이너 런타임 정책이 별도로 트래픽을 차단할 수 있습니다. 이후 초기 설정 단계에서 iptables와 nftables의 동작을 함께 확인하도록 가이드에 반영했습니다.

Retrospective

배운 점 & 개선사항

배운 점

StatefulSet을 직접 다뤄보고 싶어서 PostgreSQL, Kafka, Debezium을 모두 Kubernetes 클러스터 내에 구성했습니다. 그러나 서비스 간 의존성이 깊어질수록 단일 장애 지점(SPOF)이 생기기 쉽고, 특히 Kafka 쿼럼 실패나 PostgreSQL securityContext 오류처럼 하나의 컴포넌트 문제가 전체 서비스에 영향을 미치는 상황을 경험했습니다.

개선사항

가용성과 보안성을 높이기 위해 StatefulSet 사용을 지양하고, DB + Kafka + Debezium을 별도 VM에 구성한 뒤 Tailscale VPN으로 K8s 클러스터와 묶어 관리하는 방식으로 개선하고 싶습니다. 이렇게 하면 인프라 레이어와 애플리케이션 레이어가 분리되어 장애 격리와 독립적인 스케일링이 가능해집니다.
