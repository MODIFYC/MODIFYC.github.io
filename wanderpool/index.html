WanderPool

실시간 카풀 매칭 MSA 서비스  ·  wanderpool.cloud

현대오토에버 클라우드 스쿨 3기(운영: 한국전파진흥협회) 4인 팀 프로젝트입니다.
물리 서버 2대 위 VM 9대로 구성한 온프레미스 Kubernetes 클러스터에 4개 마이크로서비스(auth·member·party·map)를 배포하고, 이후 AWS EKS로 마이그레이션했습니다.
저는 네트워크·인프라 설계, CI/CD 구축, 모니터링·로깅 AI 파이프라인, AWS 마이그레이션을 맡았습니다.

BEFORE 게이트웨이 도입 전

클라이언트가 각 서비스로 직접 요청. 서비스마다 인증/인가 로직이 중복되고, 클라이언트가 보낸 헤더를 그대로 신뢰해야 하는 위험이 있었으며 진입점이 분산되어 있었습니다.

AFTER Kong 도입 후

Kong Gateway를 단일 진입점으로 사용. Route를 Public(auth)/Protected(member·party·map)로 분리하고, Protected 요청은 JWT를 검증한 뒤 클라이언트 식별 헤더를 제거하고 검증된 Claim 기반 헤더로 교체합니다.

CI/CD Pipeline

FE: GitLab CI(TypeCheck·ESLint) → Vercel  ·  BE: Jenkins(JaCoCo·SonarQube) → Harbor → GitOps Repo → ArgoCD → Argo Rollouts Canary 배포

역할 분리
  • 프론트엔드 & GitOps (본인 담당) GitLab CI에서 MR 시점에 TypeCheck·ESLint 검증 후 Vercel 배포, GitOps 저장소는 kubeconform·kube-score로 매니페스트 검증. 코드·매니페스트 검증이 병합 전에 끝나도록 구성
  • 백엔드 (팀원 담당) Jenkins가 코드 품질(JaCoCo·SonarQube) 검사 후 Harbor에 이미지 Push, GitOps 저장소 이미지 태그 갱신 → ArgoCD가 감지해 Argo Rollouts로 Canary 배포

왜 BFF(Backend For Frontend)인가

브라우저가 백엔드 서비스를 직접 호출하면 백엔드 URL과 토큰이 클라이언트에 그대로 노출됩니다. Next.js Route Handler를 BFF로 두어 OAuth 콜백 수신과 토큰 처리를 서버 쪽에서 전담하게 하고, 브라우저는 baseURL=''로 BFF만 경유하도록 구성했습니다.

  • HttpOnly 쿠키 토큰을 HttpOnly 쿠키로 관리해 XSS로 인한 토큰 탈취 방어
  • 환경변수 분리 서버 전용 변수와 NEXT_PUBLIC_*클라이언트 노출 변수를 명확히 구분해 민감한 값이 번들에 섞여 들어가지 않도록 관리

Kong vs Spring Cloud Gateway
문제
4개 마이크로서비스마다 인증 로직이 중복되고, 클라이언트가 보낸 헤더를 그대로 신뢰하는 구조
고민
Spring Cloud Gatewayvs Kong
결정
Kong 도입
이유
Spring Cloud Gateway는 게이트웨이 정책 변경에도 애플리케이션 재배포가 필요. Kong은 인증 정책을 Kubernetes 리소스(KongPlugin CRD)로 선언해 GitOps로 관리 가능
결과
인증을 게이트웨이에 중앙화, 서비스는 검증된 요청만 수신
MetalLB 도입 검토 → 배제
문제
온프레미스 클러스터의 외부 진입 경로 필요
고민
MetalLB(표준 방식)vs NodePort + Kong
결정
MetalLB 미도입
이유
VirtualBox NAT Network 구조에서 L2 모드의 ARP 브로드캐스트가 호스트에 도달하지 못함. 패킷 추적으로 원인 규명
결과
NodePort로 진입하고 Kong이 서비스별 라우팅 담당. 표준이 항상 정답은 아니라는 것을 확인
GitLab CI vs Jenkins
문제
빌드 성격이 다른 여러 파이프라인을 어떤 도구로 운영할 것인가
고민
팀 전체 Jenkins 통일vs 파이프라인별 분리
결정
백엔드는 Jenkins(팀원 담당), 프론트엔드·GitOps 저장소는 GitLab CI(본인 담당)
이유
매니페스트 검증은 별도 빌드 서버가 아니라 코드가 있는 곳에서 병합 전에 끝나야 함. GitLab MR 이벤트(merge_request_event)에 직접 연결해 kustomize build로 렌더링한 최종 매니페스트를 검증하도록 구성. kubeconform(-strict)은 스키마·타입 오류를 잡아 실패 시 병합을 차단하고, kube-score는 베스트프랙티스를 점수로 리포트만 하는 비차단 권고로 분리
결과
도구 통일보다 파이프라인 성격에 맞춘 구성. 배포를 깨뜨리는 문제는 강제 차단, 개선 권고는 비차단으로 나눠 파이프라인이 과도하게 막히지 않으면서도 품질 신호는 남도록 함
Lambda 역할 분리 (수집 / 분석)
문제
관측 데이터 수집과 LLM 분석·전달을 한 함수에 둘 것인가
고민
단일 Lambdavs 역할별 분리
결정
수집 Lambda(VPC 내부) / 분석·보고 Lambda(VPC 외부)로 분리, S3를 경계로 사용
이유
  • 관심사 분리 수집(적재)과 분석·전달(LLM 호출·알림)은 책임이 다른 작업
  • 최소 노출 수집은 사설망에만, 보고서는 외부 API(Bedrock·Slack)에만 접근. 한 함수에 사설망과 인터넷을 동시에 열지 않음
  • 운영·비용 효율 사설망 접근은 VPC 내부(S3 Gateway Endpoint), 외부 호출은 VPC 외부. 두 영역을 잇는 상시 NAT Gateway 불필요
결과
최소 권한 원칙 적용, NAT Gateway 비용 절감, 운영 단순화

Operations

재해복구(DR) 계획 · 런북

이미 구축된 시스템을 네트워크 · Kubernetes · DB · 외부 연동레이어별로 분리해, 각 계층에서 발생할 수 있는 장애 시나리오와 복구 절차를 설계·문서화했습니다. 직접 구현한 인프라를 새로 만든 것은 아니고, 이미 만들어진 시스템을 운영 관점에서 다시 들여다보며 대응 체계를 정리한 작업입니다.

장애 등급 정의
등급 장애 범위 예시
L1 Pod 단위 특정 마이크로서비스(party, member 등) Pod CrashLoopBackOff
L2 Worker Node 단위 worker1 또는 worker2 다운
L3 Host PC 단위 K8s용 또는 DB용 Host PC 1대 전체 다운 (Host PC 2대를 K8s용·DB용으로 분리 운영 중)
L4 학원 네트워크·전원 전체 장애 정전, 네트워크 완전 단절 등 외부 도달 불가 상황

L1은 K8s의 Probe 기반 자동 재시작과 ArgoCD GitOps 재배포에 더해, AlertManager 실시간 알림과 Lambda 기반 일일 Bedrock 요약(AI Observability Pipeline 참고)까지 이중으로 탐지되고 있습니다. L2는 Kong이 replica 2 + podAntiAffinity로 노드 분산 배치되어 있고 각 서비스도 HPA minReplicas 2가 기본값이라 단일 노드 장애에 대한 기본 대응력은 갖췄지만, 실제 노드 장애 재현 테스트까지는 하지 못했습니다. L3(Host PC 전체 장애)는 문서화 과정에서 GitOps 저장소와 컨테이너 레지스트리가 K8s 클러스터와 같은 호스트 위에 있어 단일 장애점이 된다는 구조적 취약점을 발견했고, 이 부분이 가장 큰 보강 대상으로 남아 있습니다.

Troubleshooting

트러블슈팅

01MetalLB L2 모드 미동작 외부 접근 불가▼
현상

MetalLB L2 모드로 서비스에 External IP를 할당했지만 외부에서 접근이 되지 않음.

원인

VirtualBox NAT Network 구조에서 L2 모드의 ARP 브로드캐스트가 호스트에 도달하지 못함.

해결

NodePort + Kong 구조로 전환. Kong이 서비스별 라우팅을 담당하도록 구성.

학습

표준 방식(MetalLB)이 항상 정답은 아니며, 네트워크 계층의 제약을 먼저 검증해야 한다는 것을 확인.

02Let's Encrypt HTTP-01 인증 실패▼
현상

인증서 발급 시도 시 HTTP-01 challenge가 계속 실패.

원인

공유기가 80포트를 외부에 개방할 수 없는 네트워크 제약.

해결

cert-manager DNS-01 challenge 방식으로 전환. Cloudflare DNS API 연동으로 인증서 자동 발급·갱신 구성.

학습

포트 제약이 있는 환경에서는 도메인 소유권 검증 방식 자체를 바꿔야 우회할 수 있다.

03AWS EKS 마이그레이션 중 Pod 무한 증식 및 OOM▼
현상

마이그레이션 중 Pod 개수가 계속 늘어나며 노드에서 OOM 발생.

원인

ArgoCD sync 문제를 먼저 의심했으나, 실제 원인은 HPA의 replica 자가복원. Deployment의 replica 수를 줄여도 HPA가 계속 원래 값으로 되돌림.

해결

HPA 설정(min/max replica, 목표 지표)을 먼저 확인·조정한 뒤 재배포.

학습

선언적 시스템에서는 증상만으로 판단하지 말고 어떤 컨트롤러(Deployment vs HPA vs ArgoCD)가 실제로 상태를 관리하는지 먼저 확인해야 한다.

04overlay 패치가 base ConfigMap의 OAuth 키를 덮어씀▼
현상

배포 후 OAuth 로그인 인증 실패.

원인

kustomize overlay 패치가 base ConfigMap 전체를 덮어쓰면서 사용 중이지 않던 OAuth provider 키까지 함께 활성화되어 충돌.

해결

실제 사용 중인 provider 값만 활성화하는 최소 변경으로 패치를 수정.

학습

overlay 패치는 필요한 필드만 최소한으로 건드려야 한다. ConfigMap 전체 치환은 예상치 못한 사이드 이펙트를 만든다.

05EKS 노드 30분간 CREATING 상태 정체▼
현상

노드 그룹 생성 후 30분이 지나도 상태가 CREATING에서 진행되지 않음.

원인

EC2 인스턴스 자체가 생성되지 않고 있음을 확인. ASG 활동 로그를 확인해 신규 계정의 프리 플랜이 유료 인스턴스 타입 생성을 차단하고 있음을 규명.

해결

유료 플랜으로 업그레이드 후 정상적으로 노드 생성 완료.

학습

클러스터 상태 메시지만 보고 판단하지 말고, 그 아래 레이어(ASG, EC2)의 실제 이벤트 로그까지 내려가서 원인을 확인해야 한다.

06사설망 Harbor → ECR 이관 시 CloudShell 접근 불가▼
현상

기존 Harbor 이미지를 ECR로 옮기려는데 CloudShell로 접근이 안 됨.

원인

기존 S2S VPN이 구 VPC 기준으로 연결되어 있어 새 VPC의 CloudShell까지 도달할 경로가 없음.

해결

Harbor가 설치된 VM을 경유지로 삼아 임시 자격증명을 발급받아 이미지를 직접 push.

학습

네트워크 경로가 바뀌는 마이그레이션에서는 기존 연결을 그대로 재사용할 수 있다고 가정하면 안 되고, 항상 실제 경로를 먼저 확인해야 한다.

07DB 인증 3단 연쇄 실패▼
현상

마이그레이션 후 서비스가 DB 인증에서 계속 실패.

원인

앱 전용 DB 사용자 미생성, 비밀번호 불일치, DB명(wp_auth) 불일치가 동시에 얽혀있었음.

해결

사용자·DB 생성, 권한 부여, 비밀번호 통일까지 단계적으로 원인을 하나씩 제거.

학습

연쇄된 문제는 한 번에 고치려 하지 말고 단계별로 하나씩 검증해야 실제 원인을 놓치지 않는다.

08Kong → 서비스 502/503 (mTLS STRICT)▼
현상

검증 단계에서 Kong을 거친 요청이 서비스에서 502/503으로 실패.

원인

Istio mTLS STRICT 환경에서 서비스 메시 밖에 있는 Kong의 요청이 인증되지 않아 차단됨을 규명.

해결

검증 단계에서는 PERMISSIVE 모드로 전환. 운영 목표는 Kong을 서비스 메시 sidecar로 편입시키는 것.

학습

mTLS 같은 보안 정책은 메시 경계 밖 컴포넌트를 예외 없이 차단할 수 있다는 것을 확인. 경계에 걸친 컴포넌트는 설계 단계에서부터 별도로 고려해야 한다.

09도메인 전환 후 로그인 실패▼
현상

Cloudflare 도메인을 온프렘 IP에서 ALB로 전환한 뒤 로그인이 되지 않음.

원인

프론트엔드 환경변수에 온프렘 시절 포트(:1002x)가 잔재로 남아있어 잘못된 주소로 요청.

해결

환경변수에서 잔재 값 제거 후 재배포.

학습

인프라 전환 시 코드·설정에 남아있는 이전 환경의 흔적까지 함께 점검해야 한다.

배운 점 & 개선사항

배운 점

온프레미스와 AWS를 연결하고 MSA를 마이그레이션하는 과정에서 개별 기술보다 네트워크 경로, 인증 경계, 배포 순서처럼 시스템 사이의 연결 조건이 안정성을 좌우한다는 점을 배웠습니다. 특히 장애를 애플리케이션 문제로 단정하지 않고 DNS, Gateway, Service Mesh, 데이터베이스까지 계층별로 확인하면서 관측 가능한 구조와 단계적인 검증 절차의 중요성을 체감했습니다.

개선사항

다음 단계에서는 환경별 GitOps 구성을 더 명확히 분리하고 배포 전 스키마·정책 검증을 자동화해 설정 변경으로 인한 장애를 줄이고 싶습니다. 또한 RTO·RPO 기준에 맞춘 복구 훈련을 정기적으로 수행하고, AI Observability 리포트에 서비스별 SLO와 추세 데이터를 연결해 장애 발생 이후의 분석뿐 아니라 이상 징후를 선제적으로 판단할 수 있도록 개선할 계획입니다.
